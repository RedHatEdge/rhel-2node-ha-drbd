Two-node store platform · Option B — DRBD

DRBD on RHEL KVM

Two RHEL 9 hosts replicating block devices directly to each other. No appliance in the data path, no shared array, and every component shipped in RHEL.

Option A
StorMagic SvSAN — a virtual storage appliance on each host presenting mirrored iSCSI, which both hosts log into.
Option B
DRBD — the RHEL-native alternative. The kernel replicates the block device itself; nothing sits between the guest and the disk. This diagram.

Nothing between guest and disk

DRBD is a kernel module. There is no appliance, no iSCSI, no extra VM to keep alive. Fewer moving parts than any shared-storage design, and every component ships in RHEL.

Protocol C means synchronous

A write is confirmed to the application only once both nodes hold it. That is what makes zero data loss possible on an unplanned failure, and it is why the replication link must be its own network.

Cross-primary, not active/passive

store-a is Primary on node1, store-b on node2. Both hosts run production workload; neither is an idle standby. The promotion preference must exceed resource stickiness or the pair silently collapses onto one node while reporting healthy.

One arbiter, one job

The third host runs corosync-qnetd only. Unlike the appliance option there is no separate storage witness to deploy — DRBD settles ownership itself, using cluster fencing.

Why there is no live migration

The single most important difference between the two options, and it is architectural — no amount of tuning changes it.

  • replication / storage path
